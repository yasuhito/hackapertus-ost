\section{概要 (Summary)}

本プロジェクトはHackApertus OST Track 2A\cite{ostchallenge}に取り組みます。
入力はスイス連邦の投票冊子(PDF)または短い参照文と、独語、仏語、伊語のいずれかで書かれた主張(claim)です。
システムは主張が原文から導けるか(0=entailment)、情報が足りないか(1=neutral)、原文と矛盾するか(2=contradiction)を判定し、判定の根拠となる原文を返します。

モデルはApertus v1.5の70Bと8Bです\cite{apertus,apertus70b,apertus8b}。
設計の中心は、モデルに引用文を書かせないことです。
スクリプトがPDFをページ単位で抽出し、対象の投票案件のページを選び、原文の区間にIDを付けます。
モデルは1件につき1回のネイティブのtool callでラベルとIDだけを返し、スクリプトがIDから原文とページ番号を復元します。
冊子を読むTask Aは70B、参照文だけのTask Bは8Bが答えます。
Task Aでは、案件のページを200から700文字の段落に分け、主張に近い上位8段落とその隣接段落だけを渡します。
段落の順位は、8Bによる主張の翻訳に対するBM25と、ローカルの多言語埋め込みを融合して決めます。
やり直しても根拠を示せない非中立の回答は、案件の全ページで1回だけ答え直します。

2026-10-16の朝、旧版(v5)のページ選択が、正解根拠のあるページの36\%をモデルに渡していなかったことがわかりました。
選択を冊子の見出しに基づく方式に直し、根拠の補完を加えた新版(70B親と8B子の2段構成)は、開発用60問(DEV60)、公開60問(PUBLIC60)、確認用60問のすべてでTask Aのmacro-F1と根拠の一致率がv5を上回りました。
その後、新版の420件では70B親の最終回答が8B子の推奨とすべて一致していたことがわかり、子をなくして1回の呼び出しで答える構成(R)に移りました(12:40 JST)。
さらに、Rに段落単位の文脈と全ページでの再実行を加えた構成を、2026-10-16 16:00 JSTから本番構成としています。
提出用の実行系での3つの問題集の平均は、Rに全ページを渡した場合と比べて、Task A F1が0.881から0.903、Hit@5が0.746から0.812に上がり、トークンは10,939から7,629/件(30\%減)、時間は3.7から4.0秒/件でした。

\section{課題と評価 (Task and evaluation)}
\label{sec:eval}

Task A(Document)は冊子PDF全体と投票案件名(vote)を、Task B(Reference)は短い参照文を受け取り、JSONLで1件につき1行を返します。
公式のSolution API Guide\cite{apiguide}によると、Task Aでentailmentまたはcontradictionと答える場合は、原文言語の逐語引用を物理ページ番号(1始まり)付きで1件以上返し、先頭5件(各約5,000文字以内)が採点されます。
Task Bの根拠は任意で採点されず、返す場合のページは\texttt{null}です。

公式の評価は非公開held-outでの3クラスmacro-F1で、根拠の正確さ、トークン数、ケースあたりの時間も見ます\cite{ostchallenge,apiguide}。
本稿では主催者の評価スクリプト(根拠の照合はrapidfuzz\cite{rapidfuzz}の部分一致)をローカルで実行し、Task AとBのmacro-F1、Hit@5(Task Aで正解根拠のある問題のうち、先頭5件の根拠に正解箇所が含まれた割合)、1件あたりのトークン数と時間、形式失敗(既定回答に退避した件数)を比べます。
データは公開データセット\cite{dataset}のtrain splitだけです。DEV60、PUBLIC60、確認用60問(30行をTask AとBの両方の形式で使用)はどれもここから選んだ60問で、すべて開発中に使ったため、本稿の数値は未知データでの性能の推定値ではありません。

図\ref{fig:pipeline}に処理の流れを示します。

\paragraph{PDF抽出とページ選択}
pypdf\cite{pypdf}でPDFをページごとにテキスト化します。ページ番号はPDFの物理ページです。
Task Aでは\texttt{document\_selection.py}の\texttt{vote\_pages}が案件のページを選びます。
連邦の冊子は、各見開きの先頭ページに\texttt{Erste Vorlage}、\texttt{Premier objet}、\texttt{Primo oggetto}のような序数の見出しを印刷しています。
見出しが1つだけ現れるページをその案件のページとし、見出しのないページは直前の見出しページに属するとみなします。
表紙や目次のように全案件の見出しが並ぶページは、どの案件にも割り当てません。
案件名とページ冒頭の語の重なりで序数を決め、一致度が0.45に届かない場合と、見出しのない冊子(単一案件など)では全ページを渡します。
選ばなかったページは空文字列に置き換えるので、ページ番号は物理ページのまま保たれ、渡していないページは根拠として返せません。

\paragraph{段落の絞り込み(Task A)}
選んだページを、空行と文の境界で200から700文字を目安とする段落に分けます(\texttt{document\_selection.py}の\texttt{paragraphs})。
段落はページ本文の連続した部分文字列で、単語の途中では切りません。
主張の言語が冊子と異なる場合は、Apertus 8B\cite{apertus8b}が主張を冊子の言語に訳します。短い呼び出しが1回増え、約100トークンをそのケースのトークンに含めます。
段落の順位は、訳文に対する単語と文字4-gramのBM25\cite{robertson2009bm25}、原文の主張の文字4-gramのBM25、静的な多言語埋め込みのコサイン類似度を順位融合して決めます。
埋め込みはmodel2vecの\texttt{potion-multilingual-128M}をint8に量子化したもの(140 MB)で、numpyだけでCPUで動きます。重みはイメージに同梱し(節\ref{sec:repro})、ローカルの埋め込みは大会の規則で許されています。
上位8段落と、それぞれの同じページ内の前後の段落を残し、続き合う段落は1つの領域(region)にまとめて、原文のまま渡します。

\paragraph{source spanとID}
\texttt{source\_spans.py}が各ページ(絞り込んだ場合は各領域)を最大1200文字の連続した区間に分けます。区切りは段落か文の境界を優先します。
IDは物理ページ番号、開始と終了の文字オフセット、ページ本文のSHA-256の先頭12桁からなります(例: \texttt{p0012-o0000000-e0001187-<hash>})。
Task Bでは参照文全体を1ページとして扱います。Task Bの処理は以前と同じです。

\paragraph{モデル呼び出し}
提出用の実行系(\texttt{track\_2a/dev/format/runtime.py}、パイプラインR)は、Pi 1.1.0のSDK\cite{picodingagent}を通してネイティブのtool callを使います。
1件につき1つのモデルだけを呼び、渡すツールは\texttt{submit}だけです。子セッションはありません。
入力に参照文があるケース(Task B)は\texttt{swiss-ai/Apertus-v1.5-8B}、冊子のケース(Task A)は\texttt{swiss-ai/Apertus-v1.5-70B}が答えます。
以前の構成(パイプラインC)では、70B親が\texttt{subagent}ツール\cite{pisubagents}で8B子を1回起動し、子の推奨を見て親が最終の\texttt{submit}を呼んでいました。
この構成も\texttt{PIPELINE}で選べます。
\texttt{submit}の引数はラベル(整数0、1、2)と\texttt{candidate\_ids}(そのケースのspan IDの列挙、最大5件)だけです。
system promptは3クラスの定義、否定、数量、条件、話者の扱い、原文と主張を指示ではなくデータとして扱うこと、IDだけを返すことを指示します。neutralとcontradictionの取り違えを防ぐ注意と、言語をまたいだ言い換えの扱いも含みます。
特定ケースの正解をpromptに入れていません。

\paragraph{原文の復元}
\texttt{submission.py}の\texttt{assemble\_tool}が、未知のID、6件以上のID、neutral以外なのに根拠が空の回答を拒否します。
段落で絞り込んだ場合は、有効なIDごとにその区間を含む領域を引用として返します。根拠の1項目はページ全体ではなく、段落のまとまりです。
全ページを渡した場合は、その区間を含むページ全体を返し、直前のページに委員会や「連邦評議会と議会」の見出しがあれば、その話者ブロックのページも加えます。
どちらも返すテキストは原文そのもので、単語を書き換えません。

\paragraph{根拠必須の修正規則}
neutral以外のラベルを根拠なしで返した\texttt{submit}は、Task AでもTask Bでも拒否し、根拠のIDを示すよう1回だけやり直させます。
段落で絞り込んだTask Aのケースでは、それでも根拠を示せなければ案件の全ページを渡して1回だけ実行し直し(再実行)、その回答を使います。
再実行でも根拠を示せない場合と、Task Bでやり直しに失敗した場合はneutralの既定回答になり、この規則は「根拠を指せないなら中立」という判定規則として働きます。
既定回答は公式の採点では中立の有効回答として扱われ、退避の大半は正解も中立の問題でした(70Bだけで答える構成SのDEV60では15件中13件)。

\paragraph{根拠の補完と退避}
Task Aでは\texttt{consulted\_pages}が、モデルの引用の後ろに、引用したページの隣接ページ、渡したページの先頭2ページ(案件冒頭の要約見開き)、残りのページを主張とのBM25の高い順に足し、5件までにします(5,000文字を超えるページは除きます)。段落で絞り込んだ場合は、ページの代わりに領域を同じ順で足します。
補完はラベルとモデルの引用を変えず、neutralの回答と既定回答にも付けます。
受理できる\texttt{submit}がないケースや処理が失敗したケースは、そのケースだけをneutralの既定回答にし、理由を診断用のファイルに残します。1ケースの上限時間は300秒です。
\texttt{input\_tokens}と\texttt{output\_tokens}はそのケースの全呼び出しのAPIの\texttt{usage}の合計、\texttt{inference\_time\_ms}は文脈の準備を含むケース全体の時間です。

\section{開発の経緯と診断 (Development history and diagnosis)}

2026-10-14に、system promptの出力指示を\texttt{submit}の引数の形式に合わせた版(v5)を採用しました(\texttt{docs/prompt-eval-log.md})。v5はDEV60の5回平均でTask A F1 0.650、Task B F1 0.815、Hit@5 0.263でした。
10-15の夜には、検証役や複数エージェントの研究\cite{dhuliawala2023cove,huang2024selfcorrect,du2023debate,smit2024mad}を動機に8Bの役を親に足す3つの構成を試しましたが、形式失敗が増え、根拠も改善しなかったので採用しませんでした。

10-16の朝、モデルを呼ばずにDEV60とPUBLIC60でTask Aの正解根拠がある39問を調べると、14問(36\%)で正解根拠のページをモデルに渡していませんでした。
旧方式は\texttt{im Detail}などの語で案件詳細節の開始を探していましたが、この語が目次ページに誤って一致し、参照文の出典になりやすい案件の要約見開き(In Kürze、En bref、In breve)が落ちていました。別に3問は、正解根拠がpypdfの抽出したどのページとも一致しませんでした。
見出しによる方式に置き換え、確認用の30行を除く公開データで、正解根拠がページと一致する501行を検査しました(表\ref{tab:audit}、個別の正解行に合わせた調整はしていません)。

ページ選択だけを直してもDEV60のHit@5は0.263のままで、モデルは正解ページを渡されても別のページを引用しました。関連箇所を入力に含めても使われるとは限らないという報告\cite{liu2023lost,hsieh2024ruler}と同じ傾向で、そこで根拠の補完を加えました。
コミット650de65では重複IDの統合、Task Bの根拠の任意化、隣接ページの補完を加え、保存済みの回答の再採点で正解根拠を含む件数が149件中89件から98件に増えました。次節の表の新版の値は、この変更より前の版によるものです。

新版の7回の実行(DEV60を3回、PUBLIC60を1回、確認用60問を3回、計420件)では、70B親の最終回答が420件すべてで8B子の推奨と一致し、親の2回の呼び出しが全トークンの63\%、待ち時間の65\%を占めていました。
そこで1つのモデルが1回の\texttt{submit}だけで答える構成として、70BだけのSと、Task Aを70B、Task Bを8Bに振り分けるRを加えました。
8Bだけの1回呼び出しはDEV60でTask A F1 0.714(テキストのJSONで答えさせると0.361)で、冊子の問題では70Bに届かないため、Task Aは70Bに残しました。
Task Bで根拠なしの非中立回答を受け入れていた間は、70Bが話題違いの主張を根拠なしで矛盾と答えてTask B F1が0.693まで落ちたので、コミット8d5c7e6で根拠必須の規則をTask Bにも戻しました。

次に、案件のページから主張に関係する段落だけを渡す方式を試しました。
公開データ610行で、残した段落のどれかが採点器の照合に通る割合は、訳文のBM25だけで0.970、埋め込みだけで0.915、融合で0.975(異言語の組で0.968)で、渡す文字数は約8,700でした。
しかし段落だけでは、Hit@5は上がってもTask A F1が下がりました(開発用の実行系でのTask A F1とHit@5は、DEV60で0.833と0.84、PUBLIC60で0.857と0.85、確認用60問で0.734と0.79)。矛盾を裏付ける箇所を引用できず既定回答に落ちる問題が増えたためで、段落を12、16に増やしても戻りませんでした(0.826、0.806)。
そこで既定回答に落ちる問題だけを案件の全ページで答え直す再実行を加えると、開発用の実行系での3つの問題集の平均Task A F1は、全ページを渡す場合の0.882に対して0.900になりました。再実行した問題は60問中11、8、6問で、そのうち6、4、3問で根拠付きの回答を得ました。

\paragraph{v5と新版}
DEV60では3回とも新版のTask A F1がv5を上回り(0.690から0.728)、確認用60問ではv5が送信上限の240,000バイトを超えた1問を既定回答かつトークン0としているため、両版が処理した59問で比べるとv5が26,420、新版が26,692トークン/件です。
新版は事前登録の基準のうちHit@5(v5より0.10以上高い、実際は+0.056)とトークン(v5以下、実際は+11\%)を満たしませんでしたが、所有者はこの2つを大会の規則にない基準として大会の評価項目で比べ直し、新版を採用しました(\texttt{docs/confirmation-protocol-2026-10-16.md})。

\paragraph{新版とR}
全ページを渡すRは3つの問題集すべてで新版よりTask A F1とHit@5が高く、トークンは半分以下ですが、確認用60問ではTask A F1の差(0.797と0.802)が偶然の範囲で、Task B F1は新版の0.929に対して0.904でした。
70BだけのSもTask A F1とHit@5で新版を上回りましたが、既定回答が多く(DEV60、PUBLIC60、確認用60問で15、10、8件)、Task Bで話題違いを矛盾と答える傾向があるため、Rを選びました(\texttt{docs/single-call-results-2026-10-16.md})。

\paragraph{全ページと段落+再実行}
3つの問題集の平均で、段落と再実行はTask A F1を0.881から0.903、Hit@5を0.746から0.812に上げ、トークンを10,939から7,629/件に30\%減らし、時間は翻訳と再実行の分だけ3.7から4.0秒/件に増えました。
Task A F1の上昇は確認用60問(0.802から0.875)によるもので、DEV60とPUBLIC60ではほぼ変わらず、Task Bは冊子を使わないのでTask B F1の差(平均0.919と0.922)は実行ごとのぶれです。

\section{限界と今後 (Limitations and next steps)}

\paragraph{評価の限界}
すべての数値は開発中に使った公開データでの値で、60問、1回から5回の実行です。採用した構成は各問題集1回しか測っていません。
公式のheld-outでの成績はわかりません。

\paragraph{抽出の限界}
前述の新版の420件のうち、Task Aで根拠が採点される149件を調べると、26件は正解の根拠文がpypdfの抽出テキストと一致しません。
この種の不一致は、根拠を領域単位にしたことで大部分が解消したと考えています。引用がページ全体より短くなり、採点器の部分一致に通りやすくなるからです。
ただし、この26件を個別に採点し直してはいません。
テキストを抽出できないPDFはOCRを行わずエラーにします。
見出しのない冊子では全ページを渡すので、入力が長くなります。

\paragraph{再実行の費用と実行環境}
再実行は、段落で根拠を示せなかった冊子の問題に呼び出しを1回足します。開発用の実行系では、60問中11、8、6問で再実行が起きました。
埋め込みの重みを同梱するDockerイメージは、開発ホストではまだbuildできていません(節\ref{sec:repro})。

\paragraph{残る分類誤り}
全ページを渡すRの3問題集(開発用の実行系、各1回、計180問)では、Task Aの誤りは90問中11件で、矛盾を中立とした5件、矛盾を含意とした3件、含意を矛盾とした2件、中立を矛盾とした1件です。Task Bの誤りは90問中6件で、矛盾を中立2件、矛盾を含意2件、含意を矛盾2件です。
根拠規則による退避13件のうち11件は正解が中立で、矛盾を取りこぼしたのは2件でした。
段落だけを渡したときのTask A F1の低下も矛盾を引用できないことが原因で、矛盾の取りこぼしは今も主な分類誤りです。ただし件数が少ないため、指示文を変える根拠はまだ弱いと考えています。

\paragraph{根拠の性質}
source IDは引用が原文のどこから来たかを保証しますが、引用が判定を支えるかどうかは保証しません\cite{gao2023alce}。
段落の絞り込みと、補完で足したページや領域は検索で選んだもので、モデルの判断ではありません。

\paragraph{今後}
採用した構成を各問題集で複数回実行し、実行ごとのばらつきを見積もります。
抽出が一致しなかった26件が領域単位の根拠で当たるかを確かめ、残るものについてpypdf以外のPDF抽出ライブラリを比べます。

\section{再現方法 (Reproducibility)}
\label{sec:repro}

提出物はDockerで動かします。
公式の契約\cite{apiguide}では、CPUのみのlinux/amd64イメージで、注入された\texttt{BASE\_URL}と\texttt{API\_KEY}をすべてのモデル呼び出しに使い(ホストの鍵は読みません)、実行時にダウンロードしないことが求められます。
\texttt{Dockerfile.agent}は、Node 26.10.0の段階で\texttt{package-lock.json}からPi 1.1.0と\texttt{@tintinweb/pi-subagents}を入れ、\texttt{python:3.11-slim-bookworm}に\texttt{track\_2a/src}と実行系をコピーし、\texttt{model2vec==0.10.0}と埋め込みの重みを\texttt{docker build}のときに同梱します。
入口は\texttt{runtime.py}で、既定は\texttt{PIPELINE=R}(\texttt{Dockerfile.agent}と\texttt{Makefile}の両方)、\texttt{CONTEXT\_SELECTION=claim\_paragraphs}、\texttt{CLAIM\_SPANS=8}です。
\texttt{ESCALATE\_ON\_FALLBACK=0}で再実行を止め、\texttt{CONTEXT\_SELECTION=vote\_pages}で案件の全ページを渡します。\texttt{PIPELINE=C}で70B親と8B子、\texttt{PIPELINE=S}で70Bだけの構成を選べます。Rでは\texttt{LLM\_MODEL}を指定しても使いません。
\begin{verbatim}
make run INPUT_DIR=/path/to/input INPUT=/data/input.jsonl \
  OUTPUT_DIR=/path/to/new/output
\end{verbatim}
出力ディレクトリには正規のJSONLのほか、\texttt{.diagnostics.jsonl}と\texttt{.evaluation.jsonl}を書きます。
開発ホストではDocker daemonを使えず、イメージのbuildとrunは確認できていません(\texttt{track\_2a/dev/format/README.md})。

開発用のハーネスでは、Pi 1.1.0を\texttt{\textasciitilde/.cache/ost-pi-1.1.0}に置き、\texttt{PI\_PACKAGE\_ROOT}と\texttt{PI\_SUBAGENTS\_ROOT}でその場所を指定します。
リポジトリURLと提出リビジョンは\TBD{リポジトリURLと最終コミット}、デモは\TBD{デモ}です。
