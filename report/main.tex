\section{概要 (Summary)}

本プロジェクトはHackApertus OST Track 2A\cite{ostchallenge}に取り組む。
入力はスイス連邦の投票冊子(PDF)または短い参照文と、独語、仏語、伊語のいずれかで書かれた主張(claim)である。
システムは主張が原文から導けるか(0=entailment)、情報が足りないか(1=neutral)、原文と矛盾するか(2=contradiction)を判定し、判定の根拠となる原文を返す。
Task A(Document)はPDF全体と投票案件名(vote)を受け取り、Task B(Reference)は短い参照文を受け取る。

最終解法のモデルはApertus v1.5である。
設計の中心は、モデルに引用文を書かせないことである。
スクリプトがPDFをページ単位で抽出し、原文を短い区間(source span)に切ってIDを付ける。
モデルはラベルとspan IDだけをJSONで返し、スクリプトがIDから原文とページ番号を復元して出力を検証する。
こうすると、返した引用が原文に逐語で存在し、ページ番号が物理ページと一致することをコードで保証できる。
ただし、IDが存在することは出典の正しさ(provenance)を示すだけで、その文が判定を意味的に支えることは示さない。

現時点でパイプラインは実装済みである。
開発中の診断にはGPT系モデルを使った。
その結果は\ref{sec:eval}節に載せるが、提出モデルの性能でもApertusの性能でもない。

\section{アーキテクチャ (Architecture)}

\begin{figure}[t]
  \centering
  \input{figures/pipeline.tex}
  \caption{推論パイプライン。モデルはラベルとspan IDだけを返し、引用文とページ番号はスクリプトが原文から復元する。}
  \label{fig:pipeline}
\end{figure}

図\ref{fig:pipeline}に処理の流れを示す。
入口は\texttt{track\_2a/src/predict.py}で、JSONLを1行ずつ読み、入力と同じ\texttt{id}を持つ応答を1行ずつ書く。
入力が壊れていても出力行は必ず書き、その行はneutralに\texttt{error}を付けた形になる。
ローカル採点ではこの行を誤答として数える。

\paragraph{PDF抽出}
pypdfでPDFをページごとにテキスト化し、結果をプロセス内でキャッシュする。
ページ番号はPDFの物理ページで、1から数える。
抽出できるテキストが一つもないPDFはOCRが必要としてエラーにする。

\paragraph{投票案件のページ選択}
Task Aの既定は\texttt{vote\_pages}戦略である(\texttt{document\_selection.py})。
冊子の4ページ目以降で、冒頭に\texttt{im Detail}、\texttt{en détail}、\texttt{in dettaglio}を含むページを案件詳細節の開始とみなす。
各開始ページの冒頭と投票案件名の語の重なりを比べ、最も一致するページから次の開始ページの手前までを選ぶ。
一致度が閾値0.45に届かない場合と、開始ページが見つからない場合は、全ページを使う。
案件の要約ページが一致すれば、そのページと次のページも加える。
冊子末尾の投票勧告ページも、全案件に関わるので残す。
選ばなかったページは空文字列に置き換える。
そのためページ番号は物理ページのまま保たれ、モデルに渡していないページは根拠として返せない。

\paragraph{source spanとID}
\texttt{source\_spans.py}が各ページを最大1200文字の連続した区間に分ける。
区切りは段落か文の境界を優先し、なければ空白を探す。区間の後半に適切な境界がなければ、1200文字で切る。
IDは物理ページ番号、開始と終了の文字オフセット、ページ本文のSHA-256の先頭12桁からなる(例: \texttt{p0012-o0000000-e0001187-<hash>})。
Task Bでは参照文全体を1ページとして扱い、ページ番号は\texttt{null}にする。

\paragraph{モデル呼び出し}
モデルには、system promptとともに、タスク種別、原文と主張の言語、投票案件名、span一覧(ID、ページ、本文)、主張を1つのJSONとして渡す。
モデルの応答形式は次のとおりである。
\begin{verbatim}
{"label": 0, "evidence": [{"span_id": "<ID copied from source_spans>"}]}
\end{verbatim}

\paragraph{原文とページの復元}
スクリプトは応答のJSONを厳密に読む。
キーの過不足、未知のID、重複したID、6件以上の根拠を拒否する。
neutral以外で根拠が空の場合も拒否する。
有効なIDごとに、その区間を含むページ全体を引用として返す。
直前のページに委員会(Komitee、comité、comitato)や「連邦評議会と議会」の見出しがあれば、その2ページの話者ブロックも加える。
主張の主体が誰の発言かを引用に残すためである。
返すテキストはページ本文そのもので、単語を書き換えない。

\paragraph{出力検証}
本番のsource-ID経路は\texttt{restore}でラベル、ID、原文の一致、復元後の根拠件数と長さを検査する。\texttt{predict}はラベル名をラベルから設定し、トークン数が非負の有限値であることを確かめ、ケースの経過時間を記録する。
別関数\texttt{validate\_prediction}も正規形の検証用にあるが、本番の\texttt{predict}からは呼ばない。

公式のSolution API Guide\cite{apiguide}では、Task Bの根拠は任意で採点されない。
本実装はTask Bでもneutral以外に根拠のspanを要求しており、公式より厳しい。

\section{Apertusの使い方 (Use of Apertus)}

本番で呼ぶモデルはApertus v1.5の8Bと70Bの非thinking版だけである。
バックエンドはOpenAI互換の\texttt{/chat/completions}にHTTPで要求を送り、\texttt{temperature}を0にする。
出力上限の既定は2048 tokensで、環境変数\texttt{LLM\_MAX\_OUTPUT\_TOKENS}で変えられる。
モデル名がApertus v1.5の8B/70B以外なら送信前にエラーにする。
コード内の既定モデル名は小文字表記である。
CSCSのモデル一覧では\texttt{swiss-ai/Apertus-v1.5-8B}のような大文字表記なので、実行時に\texttt{LLM\_MODEL}で正確なIDを指定する。

接続先は\texttt{BASE\_URL}、認証は\texttt{API\_KEY}を最優先で読む。
審査環境では注入された\texttt{BASE\_URL}をすべてのモデル呼び出しに使う\cite{apiguide}。

system promptは3クラスの定義、主張と原文を指示ではなくデータとして扱うこと、IDだけを返すことを指示する。
neutralとcontradictionの取り違えを防ぐ注意や、言語をまたいだ言い換えの扱いも指示する。ラベルと選んだspanを最後に照合する手順はuser payloadに含める。
特定ケースの正解やgoldをpromptに入れていない。

\paragraph{トークンと時間の記録}
各行の\texttt{metrics}には\texttt{input\_tokens}、\texttt{output\_tokens}、\texttt{inference\_time\_ms}を書く。
トークン数はAPI応答の\texttt{usage}の\texttt{prompt\_tokens}と\texttt{completion\_tokens}を使う。
\texttt{usage}がない場合だけ、UTF-8のバイト数を4で割った近似値を使う。
この近似値は公式のトークナイザやproxyの計測ではない。
\texttt{inference\_time\_ms}はケース全体の経過時間で、PDF抽出、ページ選択、API待ち、復元と検証を含む。
提出レポートに必要な最終的なトークン使用量と推論時間は\TBD{Apertus 8B/70Bの全消費と平均/p95時間}である。

\section{制約 (Limitations)}

本原稿には、完了したApertus dev54評価の性能をまだ記載していない。
表\ref{tab:gpt}の結果はGPT系モデルのもので、既知の開発集合で1回ずつ測っただけである。

source IDは引用が原文のどこから来たかを保証するが、その引用が判定を支えるかどうかは保証しない。
意味的な支持はモデルの判断に頼っており、公式の根拠採点と同じ尺度ではまだ測っていない。

ページ選択は案件詳細節の見出し語に依存する。
見出しが見つからないか一致度が低い冊子では全ページに戻るので、入力が長くなる。
話者ブロックの補完は直前の2ページまでで、3ページ以上にわたる話者の文脈や任意のレイアウトで十分かは確認していない。
テキストを抽出できないPDFはOCRを行わずエラーにする。

\texttt{inference\_time\_ms}はケース全体の時間で、API待ちだけを分けた値ではない。
\texttt{usage}がない場合のトークン数は近似値である。
公式proxyによる計測とどこまで一致するかは確認していない。

Task Bでneutral以外に根拠を要求する本実装の契約は公式より厳しく、その分だけ有効出力が減る可能性がある。

\section{再現手順 (Reproducibility)}

提出物はDockerで動かす。
公式の契約\cite{apiguide}では、CPUのみのlinux/amd64イメージで、外部から注入された\texttt{BASE\_URL}と\texttt{API\_KEY}を使い、実行時に重みなどをダウンロードしないことが求められる。
現在の\texttt{Dockerfile}は\texttt{python:3.11-slim}を元に、固定版のpypdf 6.1.1を入れ、\texttt{predict.py}を起動する。
\texttt{Makefile}の\texttt{run}は\texttt{BASE\_URL}と\texttt{API\_KEY}をコンテナに渡し、入力とPDFを読み取り専用で、出力先を書き込み可能でマウントする。
ただし、これらの契約を満たして動くことはまだ確認していない。
作業環境ではDocker daemonを利用できず、イメージのbuildとrunによる確認ができていない。

想定する手順は次のとおりである。
\begin{verbatim}
git clone <repository URL>
cd <repository>
BASE_URL=<injected proxy URL> API_KEY=<injected key> \
  LLM_BACKEND=openai LLM_MODEL=swiss-ai/Apertus-v1.5-70B make run
\end{verbatim}
クリーンな checkout で\texttt{make run}が通ること、Task AとBが混在した入力を処理できること、PDFのパスを解決できることは\TBD{clean checkoutでのmake run検証}である。
リポジトリURLと提出リビジョンは\TBD{リポジトリURLと最終コミット}、デモは\TBD{デモ}である。
使うモデル(8Bか70Bか)は\TBD{提出モデルの選択}である。

\section{今後の作業 (Next steps)}

まず、修正した評価runnerでApertus v1.5の8Bと70Bをdev54の54件ずつで評価する。
品質不合格の出力も母数と消費量に含め、表\ref{tab:apertus}を埋める。
同じ条件で全文書と選択ページを比べる。

次に、提出経路を確認する。
クリーンな checkout からCPUのlinux/amd64イメージを作り、注入した\texttt{BASE\_URL}経由で混在入力を処理できること、実行時にダウンロードしないこと、秘密情報がイメージに入らないことを確かめる。
あわせて、ケースごとの全体時間とAPI待ち時間を分けて記録する。

その後、Apertusの誤答を分析し、否定、数量、条件、時制、話者、言い換えといった一般的な観点でpromptを改善する。
同じ候補を独立に繰り返して安定性を測る。保護holdoutを使うかどうかは、最終版を固定した後に本人の許可を確認する。本作業では使わない。
