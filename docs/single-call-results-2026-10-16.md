# 1回呼び出し構成の比較（2026-10-16 午後）

## 背景

新版（70B親 + 8B子、コミット 76a0e6e 以降）の実行記録 420 件を調べると、70B 親の最終回答は 8B 子の提案と 420 件すべてで一致していた。親の 2 回の呼び出し（資料を読んで「子を呼ぶ」と返す 1 回と、子の答えを写す 1 回）が全トークンの 63%、待ち時間の 65% を占めていたので、1 回の呼び出しで済む構成を実行系に追加して測った。

- **S**: 1 つのモデルが 1 回のネイティブツール呼び出し（submit のみ）で答える。子セッションなし。
- **R**: S と同じだが、入力の構造で振り分ける。冊子を読む Task A は 70B、参照文だけの Task B は 8B。

どちらも、根拠を 1 つも示せない非中立回答は却下して 1 回だけやり直し、それでも示せなければ既定の中立回答にする（コミット 8d5c7e6 で Task B にもこの規則を戻した。外していた間、70B は話題違いの主張を根拠なしで「矛盾」と答え、Task B の F1 が 0.693 まで落ちた）。

温度 0 だが、同じ入力でも実行ごとに数件の差が出る。以下は各 1 回の実測で、差が 0.03 程度なら偶然の範囲と見るべき。

## 判断

S と R はどちらも、3 つの問題集すべてで現行を上回る。Q の 3 問題集平均は S 0.895、R 0.905。差は偶然の範囲だが、R は退避が少なく、トークンが約 8% 少なく、Task B で 70B の「話題違いを矛盾と言う」傾向を避けられる。**R を本番構成にする。** 切り替えは `PIPELINE` 環境変数 1 つで、`S` や `C` に戻せる。

## 8B 単独について

8B だけの 1 回呼び出し（S、8B）は開発用60 で Task A F1 0.714、Task B 0.808〜0.883、トークン 8,455、時間 2.3 秒。現行と同等の精度を 1/3 のトークンで出すが、70B の文書問題の精度には届かない。テキスト JSON 出力にすると Task A F1 は 0.361 まで落ちるので、ツール呼び出し形式が必須。

## 主張に関係する箇所だけを渡す実験（13:00〜13:20 JST、不採用）

他チームの比較メモ（主張に関係する箇所を先に検索して渡し、トークンを 1/20 にしている）を受けて、議案のページの中からさらに絞る方式を試した。検索はモデルを使わず、主張と区間の文字 4-gram の一致（BM25）で行う。単語一致では異言語の組で正解ページを半分も当てられないが、文字 4-gram なら異言語でも 0.86（上位 8 区間）まで当たる。

公開データ 610 行での正解ページ包含率と文字数（`track_2a/scripts/audit_claim_retrieval.py` と同じ手順）:

| 渡す範囲 | 包含率（全体 / 異言語） | 文字数／問 |
|---|---:|---:|
| 議案の全ページ（現行） | 1.00 / 1.00 | 32,969 |
| 要約見開き + 上位 8 区間 | 0.87 / 0.86 | 10,540 |
| 要約見開き + 上位 8 区間のページ全体 + 隣接ページ | 0.97 / 0.95 | 20,965 |

開発用 60 問での実測（R、各 1 回）:

| 渡す範囲 | Task A F1 | Task B F1 | Hit@5 | トークン／問 | 時間／問 |
|---|---:|---:|---:|---:|---:|
| 議案の全ページ（現行） | 0.875 | 0.853 | 0.74 | 11,004 | 3.0 秒 |
| 要約見開き + 上位 8 区間 | 0.801 | 0.853 | 0.74 | 4,918 | 2.5 秒 |
| 同、上位 12 区間 | 0.780 | 0.853 | 0.74 | 5,838 | 2.7 秒 |
| 要約見開き + 上位 8 区間のページ + 隣接 | 0.819 | 0.853 | 0.63 | 7,963 | 2.7 秒 |

Task A の F1 が 0.06〜0.10 落ちる。変化した 6 問のうち 4 問は正解の根拠が渡した範囲に入っていなかった。主指標の macro-F1 を落としてまでトークンを減らす判断はしない。`--selection claim_spans` / `claim_pages` は実行系に残してあるが、既定は `vote_pages` のまま。

さらに減らすには、言語をまたぐ検索の精度が要る。候補は、8B に主張を冊子の言語へ訳させてから一致させる方法（追加の小さな呼び出し 1 回、新しい依存なし）と、多言語の埋め込みモデルをローカルで動かす方法（Docker に重みを同梱、CPU で実行）。どちらも未実装。

## 翻訳を使った絞り込み（13:00〜13:40 JST、既定にはしない）

他チーム 3 つの公開実装を読むと、共通して「主張に関係する数段落だけを渡す」方式で、言語の壁は 8B による主張の翻訳か、小さな多言語埋め込み（約 100 MB、ビルド時に同梱）で越えていた。こちらでは翻訳の方を試した。

- 8B で主張を冊子の言語へ翻訳（649 件、合計 68,860 トークン、1 件あたり約 106 トークン、2 分）。キャッシュは `output/validation/claim-translations.json`。
- 訳文に対する単語 BM25 と文字 4-gram BM25 を順位融合して区間を選び、その区間のページ全体と隣のページ、要約見開きを渡す（`claim_pages`、上位 8 区間）。

公開データ 610 行での正解ページ包含率: 翻訳なし 0.97 → 翻訳あり 0.99（異言語 0.95 → 0.99）。文字数は約 19,800（議案の全ページは 32,969）。

実測（R、各 1 回。`vote_pages` の開発用は 2 回とも同じ値）:

| 問題集 | 指標 | 議案の全ページ（現行） | 翻訳＋上位 8 区間のページと隣 |
|---|---|---:|---:|
| 開発用60 | Task A F1 / Hit@5 | 0.875 / 0.74 | 0.844 / 0.68 |
| 公開60 | Task A F1 / Hit@5 | 0.967 / 0.75 | 0.933 / 0.70 |
| 確認用60 | Task A F1 / Hit@5 | 0.804 / 0.75 | 0.833 / 0.75 |
| 3 セット | トークン／問 | 約 11,000 | 7,400〜8,300（翻訳分 約 40 を含まず） |
| 3 セット | 時間／問 | 3.0〜3.1 秒 | 2.6〜3.2 秒（翻訳の呼び出しを含まず） |

Task A の F1 は 3 セット平均で 0.882 → 0.870、Hit@5 は 0.747 → 0.710、トークンは約 30% 減。差はどれも各セットで 1〜2 問の範囲で、偶然と区別できない。他チームの 10 分の 1 には届かない（要約見開きとページ単位を保つため）。

判断: 主指標を落とす可能性がある一方、効率の相対評価でどれだけ得るかは他チームの提出次第で不明。**既定は議案の全ページのままとし、`claim_pages` は選択肢として残す。** 本番の実行系（`runtime.py`）にも 8B の翻訳呼び出しを組み込んだ（13:45 JST）。`CONTEXT_SELECTION=claim_pages` で有効になり、異言語の文書問題だけ翻訳を 1 回呼ぶ。翻訳の使用量はその問題のトークンに加算され、`tmp/format-runtime/translations.jsonl` に記録される。翻訳が失敗した場合は原文の文字 4-gram で検索して続行する。既定は `vote_pages` のまま。4 問の実呼び出しで動作を確認した。
